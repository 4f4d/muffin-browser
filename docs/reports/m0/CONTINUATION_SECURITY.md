# M0a continuation security assessment

The supported design is a native-owned browser shell with a trusted chrome WebView and separately constructed untrusted browsing WebViews. Use the evidence below to guide the provisional WRY + TAO implementation decision. [Prior S1 assessment](S1_FOLLOW_UP_SECURITY.md), [pinned IPC source audit](evidence/continuation-s7-ipc-source.txt)

| Requirement | Direct fixture evidence | Native adapter work and open checks |
|---|---|---|
| Chrome-only dispatcher and private resources | Two Mac runs bracketed untrusted attempts with two trusted calls. In each run exactly two canary commands were accepted. The private chrome resource rendered in chrome and could not be fetched by the sampled content page. | Register capability handlers only in trusted chrome. Require exact method, origin and resource path, and a restrictive CSP. Use distinct contexts and content managers where registration can propagate. Real product command effects remain untested. |
| Remote IPC, subframes and request validation | Remote boundary probes on Mac produced no extra admitted command. S2a popup-ready reports from Mac, Server and the Xvfb click reported no fixture IPC shim. The S7 policy model rejects wrong view, subframe, unsupported command, wrong origin and wrong body shape. | The model uses native-authoritative facts as inputs. Actual subframe isolation and metadata delivery remain unverified for the product across engines. Never read origin, frame role, view identity or document generation from a page-supplied body. |
| Origins, redirects, popups and opener | Local same-origin popups could read the opener while cross-origin ones could retain the handle without direct document reads. Both redirect classes reached selected loopback endpoints on Mac and Server. Explicit and implicit noopener cases had no opener. The Mac message destination was explicitly scoped. | Recheck every navigation/redirect and handle popups as untrusted children of untrusted views. Keep chrome out of opener relationships with content. Maintain user-activation and popup-close decisions in the native adapters. Unexpected multi-platform redirects and frame provenance still require checks. |
| File URLs and external protocols | The bundled-file fetch rejected in the Mac fixture. The fixture page remained visible after the file navigation attempt, and the final URL and responsible layer remained unresolved. The programmatic synthetic protocol route was denied by host policy on Mac and Server. | Require user selection with a narrow native resource grant for local-file opens. Deny external protocol paths by default, then require validated initiator, current document and explicit user action where supported. No real OS protocol launch was exercised. |
| Download destinations and marks | The WRY fixtures wrote two exact synthetic payloads to distinct scratch files, rejected a denied attachment, and inspected the platform metadata markers. Windows S4 used explicit browser arguments that omit the WRY feature-disable entry for SmartScreen. | Validate the destination resolved by native code. Require race-safe file creation and safe filenames. Validate real origins, private-window behavior, Mark-of-the-Web/quarantine enforcement, and Windows runtime protections before release. |
| Renderer process termination and stale requests | Existing GTK S1 deliberately terminated the renderer through the engine API and reloaded the approved fixture route. The mock model denies an old epoch after a new document commit or recovery. | On main document commit, view reuse, renderer termination and recovery, rotate the per-view native document identity and cancel queued work from the old identity. Unexpected process recovery and native dispatch with trusted epoch/frame data remain open. |

## Native metadata boundaries

- macOS WRY passes the WKScriptMessage frame request URL to its common IPC closure. The native frame can also expose origin and main-frame information, which the common callback does not retain. The WRY shim is injected only into the top frame. Enforce authority with native sender metadata and isolated configuration, including when WebKit supplies a related configuration for popup creation. [IPC source](evidence/continuation-s7-ipc-source.txt), [Apple frame metadata](https://developer.apple.com/documentation/webkit/wkscriptmessage/frameinfo)
- Windows WRY listens to WebView2 WebMessageReceived and passes its document Source URI and string body. Treat the per-view event attachment and exact committed document as separate facts. Bind a trusted generation in native code. Do not assume a custom scheme uses the same origin representation as WKWebView. [IPC source](evidence/continuation-s7-ipc-source.txt), [Microsoft message metadata](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2webmessagereceivedeventargs?view=webview2-1.0.4022.49)
- GTK WRY maps its IPC shim to TopFrame. The underlying UserContentManager callback gets WRY's captured current WebView URI rather than the actual sending frame's origin. The custom scheme is registered on the WebContext. Keep the trusted manager and context separate and validate the native view identity when routing resources. Keep subframes out of bundled chrome. If the selected native path cannot establish the necessary sender facts, its privileged handling needs a different binding before use. [IPC source](evidence/continuation-s7-ipc-source.txt), [WebKitGTK message signal](https://webkitgtk.org/reference/webkit2gtk/stable/signal.UserContentManager.script-message-received.html)

## Policy test limits

The executable S7 contract cases cover a positive request and negative examples for wrong view, non-main frame, prior document, wrong URI, malformed/unknown command, exact resource path, redirect outside the fixture origins, file navigation and unsupported schemes. They exercise a proposed authorization rule in memory, using synthetic identities and an inert command. Production native binding and real application command dispatch remain future work. [Policy fixture](../../../spikes/s7/policy_fixture.py), [verification output](evidence/continuation-s7-checks.txt)
