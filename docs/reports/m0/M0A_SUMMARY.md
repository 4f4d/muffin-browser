**Engineering disposition:** S1 has mixed evidence and the substrate decision remains open. WRY + TAO is the first candidate for a focused follow-up. Stock Tauri failed positioned child layout on both tested Linux backends. The Mac programmatic-focus result remains negative for this fixture, and several S1 criteria still lack evidence. ## Scope and method

The bare engine floor ran before S1. The two minimal CI workflows were set up alongside the remote engine floors because those probes needed runners. Each started spike has a committed pre-start header and generated start status, followed by a final report and regenerated status. The project guard validates the Git records separately from the native fixtures. One final report commit landed in the same one-second clock tick as its stop. The guard caught it and a fresh commit recorded the reviewed reports using the actual later clock, with the start and stop fields preserved. [Clock check](evidence/report-clock-check.txt) All artifacts used deterministic loopback fixtures or `about:blank`. Current platform-level release, functional, smoke and build cells still concern the product, and these experiments use separate spike records. [Environment probe](evidence/environment-probe.txt), [spike reports](spikes/), [attempt log](../../BLOCKERS.md)

Capabilities used were the configured Codex explorer, docs researcher, separate-worktree spike writer and independent reviewer. Git worktree and versioning skills supported isolation and the report lifecycle. The CI automation skill supported immutable action pins and scoped artifacts. The verification and code-review skills were used for suite, artifact and claim checks. GitHub's connector and CLI supplied runner records. The desktop probes used AppKit/WindowServer, native Windows window capture, Xvfb and headless Weston. [Dated primary source checks](evidence/source-checks.tsv)

## Native capability matrix

All observations concern the named fixture and environment. Windows and Linux GitHub jobs ran on standard hosted VMs. The X11 server capture ran in an isolated Ubuntu container using the physical host kernel and CPU with Xvfb. Pixel decoding confirmed both WRY X11 captures contain the expected 270×144 red overlay and the stock Tauri X11 capture contains no pixels in that fixture color. Wayland fixture stdout provides functional child-view observations. [Runner documentation](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), [physical-host probe](evidence/ssh-linux-preflight.txt), [pixel check](evidence/s1-image-check.txt)

WRY loopback documents reported no `window.ipc` or `window.__TAURI_INTERNALS__` in the inspected runs. Tauri loopback documents reported both as objects on Windows and Linux. The Tauri fixture registers no privileged command and supplies no runtime proof of privileged reachability. Verify the actual chrome command/capability boundary before any product integration. [WRY fixture](../../../spikes/s1/wry-tao/src/main.rs), [Tauri capabilities](../../../spikes/s1/tauri/src-tauri/capabilities/chrome.json), [runtime source checks](evidence/source-checks.tsv)

WRY's ordinary Linux child-window construction is documented for X11. The experiment used `build_gtk` with `gtk::Fixed` for both Linux backends. Stock Tauri's tagged Linux child constructor uses the default GTK vertical box, consistent with the observed stacked panes. Windows offers a native WebView2 accelerator callback. On GTK, the M0a fixture used the native process termination signal and explicit test API. Recovered DOM viewports returned to 900×548 after a larger resize reading. The tests establish deliberate termination and local reload. Retaining resized geometry and handling an unplanned crash remain open. Shipping behavior for input, process recovery, profiles, downloads, PDF, media and permissions still needs platform evidence. [Version-specific API and policy references](evidence/source-checks.tsv)
