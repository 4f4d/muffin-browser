### Linux DL-01 investigation

The same local Ubuntu ELF received the fixture attachments under Xvfb and headless Weston, then WebKitGTK 2.52.6 reported destination errors. The hosted Xvfb binary reported two successful native completions, but the outer verifier found zero matching payloads in the app's download directory. Its verifier filters on filename location, size and digest and retains the count of matches. The old receipt cannot distinguish absent files, alternate placement or different bytes. The HTTP status and completion events establish separate parts of the transfer. [Local Xvfb](evidence/m0b-validation/linux-host-3f883-x11-first.log), [local Weston](evidence/m0b-validation/linux-host-3f883-wayland-first.log), [hosted receipt](evidence/m0b-validation/linux-ci-3f883-summary.json), [verifier](../../../spikes/m0b-validation/fixtures/run_native.py)

The final Linux adapter sets the destination in the context's download-start callback and counts the engine's terminal notification as completion without a filesystem check. WRY 0.57.2 sets its path in the per-download `decide-destination` callback after the response. The tagged WebKitGTK 2.52.6 implementation also supports an early assigned absolute path and separates file creation, data writes and the final move. Each of those filesystem stages can produce a destination error. This narrows investigation to native destination selection or persistence and what the verifier can observe. It does not establish a URI-format, timing, permission or sandbox root cause. Earlier source `623d39b` already tried `decide-destination` with a file URI. Switching callbacks alone would repeat part of an earlier attempt. [Final GTK adapter](../../../spikes/m0b-validation/src/platform/linux.rs), [download state](../../../spikes/m0b-validation/src/downloads.rs), [earlier implementation](https://github.com/4f4d/muffin-browser/blob/623d39b4fd037d60ac5f0eb1fdba0e2dd02bdd6d/spikes/m0b-validation/src/platform/linux.rs), [WRY 0.57.2](https://github.com/tauri-apps/wry/blob/wry-v0.57.2/src/webkitgtk/web_context.rs#L314-L372), [WebKitGTK destination API implementation](https://github.com/WebKit/WebKit/blob/webkitgtk-2.52.6/Source/WebKit/UIProcess/API/glib/WebKitDownload.cpp), [WebKitGTK file handling](https://github.com/WebKit/WebKit/blob/webkitgtk-2.52.6/Source/WebKit/NetworkProcess/soup/NetworkDataTaskSoup.cpp#L1090-L1179)

The existing retry limit is reached. This checkpoint used source and evidence review only. If the owner authorizes another bounded attempt, one useful discriminator is to correlate the approved path with `created-destination`, retain the native error class, and record sanitized file presence, byte count and digest from the app at completion and from the harness after exit. Keep the fixture and destination disposable. Keep Linux DL-01 held until the expected bytes are verified under the selected destination. [Attempt log](../../BLOCKERS.md), [independent handoff](M0B_VALIDATION_REVIEW.md)
