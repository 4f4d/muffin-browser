# M0b validation build security assessment

## Ownership and command path

The native shell owns browser windows, tab IDs, navigation policy, download destinations and the engineering diagnostic controls. A separate incognito WebView hosts the bundled chrome HTML. It serves no network resources, restricts navigation to the bundled document and initial empty page and rejects new windows. Its CSP blocks connections, frames and non-inline resources. Content and popup WebViews are built separately and receive no Muffin IPC, host objects, custom Chrome scheme or injected browser command bridge. WebView2 additionally disables web messages and host objects through native settings. [Chrome template](../../../spikes/m0b-validation/src/chrome.html), [view construction](../../../spikes/m0b-validation/src/main.rs), [WebView2 adapter](../../../spikes/m0b-validation/src/platform/windows.rs)

Native code polls a bounded queue through the retained chrome WebView after the local document loads and checks its current URI. WKWebView and WebKitGTK load the bundled HTML at `about:blank`. On WebView2 the only command-bearing document is the exact view-local intercepted resource of the bundled HTML. The Windows handler checks the native WebView ID, HTTP method, scheme, authority and path. Content views have no matching resource handler, and their navigation policy denies the reserved host. Only native responses to its own outstanding request serial are read. The Rust enum accepts the closed set of chrome actions, validates request size and applies navigation policy separately. Engine strings are passed into the chrome view as encoded JSON and displayed as text. A renderer reset discards the outstanding chrome poll and reloads the bundled document. Real keyboard events use AppKit, GTK or WebView2 routing. A script-generated DOM keypress supplies no host command. [Dispatcher](../../../spikes/m0b-validation/src/main.rs), [policy](../../../spikes/m0b-validation/src/policy.rs), [platform adapters](../../../spikes/m0b-validation/src/platform/)

WRY's GTK message callback supplies the captured top-level WebView URI instead of the sending frame's authoritative identity. The application avoids relying on that metadata by registering zero WRY message handlers. GTK allocates a new content manager per newly built view. Related popup configuration belongs to the untrusted opener and is checked for the expected storage mode. The private chrome store is never an opener. [Prior pinned-source assessment](CONTINUATION_SECURITY.md), [source audit artifact](evidence/continuation-s7-ipc-source.txt), [WebKitGTK user content message API](https://webkitgtk.org/reference/webkit2gtk/stable/signal.UserContentManager.script-message-received.html).

## Navigation, storage and downloads

HTTP(S) addresses with a host and no embedded credentials may navigate. The fixture mode additionally restricts main navigations to its two exact loopback origins. The engine handles normal subresource requests, certificate behavior and file upload selection. External protocols and top-level file navigation are denied by the app. WebView2 also cancels its native external URI launch event. The validation scope includes safe upload through the engine's user-mediated chooser and engine-backed downloads. [Navigation policy](../../../spikes/m0b-validation/src/policy.rs), [Windows adapter](../../../spikes/m0b-validation/src/platform/windows.rs)

Each private tab uses its own native ephemeral store. Related popups inherit the opener relationship, and popups close when their owning view is released. At construction the adapter verifies ephemeral state through WKWebsiteDataStore, WebKitGTK or the WebView2 native profile. WebView2 private views also use disposable runtime directories. On Windows, engine file locks and abrupt exits may leave runtime scaffolding. Normal and private cookie/local storage isolation is checked using synthetic state before and after app exit. The app makes no private history database or sync facility. [View lifecycle](../../../spikes/m0b-validation/src/main.rs), [runtime probes](../../../spikes/m0b-validation/src/smoke.rs)

Downloads validate their web URL before using an application-generated path. A unique directory is created atomically under the user-approved destination and the filename is reduced to a safe basename. No download path is passed to the chrome document. The Windows adapter does not request WRY’s default disabled SmartScreen feature. Actual vendor download protections require their own evidence, including for real origins. [Download allocator](../../../spikes/m0b-validation/src/downloads.rs), [WebView2 adapter](../../../spikes/m0b-validation/src/platform/windows.rs)

## Coverage and remaining risk

Tests run a positive chrome command, then have synthetic content attempt a browser command through the available page-side message surfaces and a synthetic DOM shortcut. They check tab counts and lack of popup effects, attempt fetches for an actual synthetic local file and a chrome-only resource, and check native window state after local-file and inert external-scheme requests. Additional unit tests cover malformed navigation, credentials and unknown commands. The harness checks the actual executable hash and exposes timeouts and missing popup behaviors. [Runtime probes](../../../spikes/m0b-validation/src/smoke.rs), [current platform evidence](evidence/m0b-validation/builds.json)

This assessment covers the temporary validation app and the tested engine versions. Engine sandbox behavior across all redirects, third-party frames and external services, native authorization for any future privileged bridge, trusted document identity after unexpected renderer loss, and browser security hardening remain open. Never use real account screenshots or raw browser state as public evidence. Diagnostics record roles, native lifecycle events, counters and runtime identity. The engineering output carries no navigation URLs, cookies, typed inputs, uploaded bytes or page titles.
